## 1. 결론 10줄

1. 이 장비에서 **KV 캐시는 MoE 후보(Gemma 4 26B-A4B, gpt-oss-20b)의 병목이 아니다.** iSWA 캐시 덕분에 f16 기준 20 KiB/토큰(+SWA 상수 ≈300 MiB), 24 KiB/토큰(+≈18 MiB) → `-ctk q8_0 -ctv q8_0` 로 128K 가 ≈1.5 / 1.6 GiB. [H]
2. KV 양자화가 결정적인 것은 **밀집 모델**(Ministral 3 8B 136 KiB/토큰, Phi-4 200 KiB/토큰). 여기서는 `-ctk q8_0 -ctv q4_0`(6.5 bpv) 가 "컨텍스트 2배" 레버. [H]
3. **TurboQuant 는 절반만 메인라인에 있다.** Hadamard 회전은 PR #21038(2026-04-01)로 머지되어 양자화 KV 에 자동 적용(끄기 `LLAMA_ATTN_ROT_DISABLE=1`), CUDA FWHT 커널은 #23615(05-25). PolarQuant 코드북(turbo2/3/4)은 업스트림 PR 전부 닫혔고 포크 TheTom/llama-cpp-turboquant 와 vLLM 에만 있음. 이 장비에서는 밀집 장문맥용 외엔 가치 낮음. [H]
4. 품질 규칙: `q8_0/q8_0` 은 f16 과 구분 불가(mean KLD ≈0.001). q4_0 **K** 가 위험(gpt-oss-20b AIME25 f16 37.9% → q8_0 37.1% → q4_0 21.7%, 회전 없으면 2.0%). **K 는 q8_0 유지, V 만 낮춘다.** [H]
5. 8GB 의 진짜 레버는 **전문가 CPU 오프로드**: `--n-cpu-moe N`/`-cmoe`, `--fit on`(기본, 여유 1024 MiB), 10월 신기능 `--moe-cache-mib N`(PR #29887, 10-07; 보고치 +15~60% 디코드). [H]
6. 디코드는 DDR5 대역폭 바운드: 전문가 전부 CPU 시 gpt-oss-20b ≈1.18 GiB/토큰, Gemma 4 26B-A4B Q4_K_M ≈0.81 GiB/토큰. 9700X + DDR5-6000 기대치 **25~35 tok/s**(모든 8GB 현장 보고가 20~35 밴드). [M]
7. 같은 GB206 다이(RTX 5060 8GB, Windows, 32GB DDR5)에서 **gpt-oss-20b `--n-cpu-moe 18`, 64K ctx → 33~35 tok/s** 실측(hindsight #2525). 5060 Ti 16GB 수치는 8GB 에 들어가는 워크로드라면 1:1 적용(Llama-2-7B Q4_0 tg128 93.5 tok/s). [H]
8. 추측 디코딩: Gemma 4 MTP(#23398)는 밀집 ~2×, **MoE 모델은 PR 저자가 "이득 없음"**; EAGLE-3 gpt-oss-20b 1.06/0.95/0.89×. 8GB 에서는 **전 레이어 GPU 상주 시에만** 이득(#25357: 12B 27.4 → 40.4 tok/s). 무료 n-gram(`--spec-default`)만 상시 ON. [H]
9. 2026 Blackwell 함정: CUDA 13.2.0/13.2.1 의 IQ1_S/IQ2_S/IQ3_S 미스컴파일(#28581), sm_120 CUDA graphs 행(#27330 → `GGML_CUDA_DISABLE_GRAPHS=1`), Windows 바이너리 b9031–b9049 CPU 폴백(#22748), Gemma 4 `--mmproj`+MTP abort(#30698), Windows 무음 스필 ≈−30%(#25357). [H]
10. 실행 레시피는 §11: Windows 는 **cuda-13.4 빌드**(12.4 빌드엔 sm_120 코드 없음), `-fa on -t 8 -np 1`, `-c` 명시, 시작 로그의 KV 버퍼·`n_rot_k/n_rot_v`·`llama_memory_breakdown_print`·`llama_moe_cache` 적중률 확인. [H]

## 2. TurboQuant 의 실체

**방법**(Google Research, ICLR 2026; arXiv 2504.19874, PolarQuant 2502.02617 + QJL 2406.03482 기반) [M, 원문 미재확인]: 헤드별 KV 벡터에 (1) 노름 분리 → (2) **Walsh-Hadamard 변환 + 무작위 부호 뒤집기**(좌표가 ~N(0,1/d) 로; 실측 첨도 900 → 2.9) → (3) 가우시안 가정 **Lloyd-Max 최적 스칼라 양자화**(16/8/4 센트로이드 = turbo4/3/2) → (4) 선택적 **QJL 1비트 잔차**(내적 비편향화). 구현 bpv: turbo4 4.25, turbo3 3.5(블록 32)/3.125(블록 128), turbo2 2.5/2.125(비교: q8_0 8.5, q4_0 4.5, f16 16). 논문 수준 주장(~3.5비트 무손실, KV ~6×, 어텐션 로짓 ~8×)은 미재확인 [M/L]. **실전 구현은 QJL 을 뺀다**(분산 증폭 → softmax 노이즈; "5개 독립 그룹 확인", vLLM 프리셋 접미사 `_nc`) [H].

## 3. 통상 KV 양자화 규칙 (llama.cpp master 소스) [H]

* 허용 `-ctk/-ctv`: `f32, f16, bf16, q8_0, q4_0, q4_1, iq4_nl, q5_0, q5_1`(기본 f16/f16). bpv(스케일 포함): f16 16, q8_0 8.5, q5_1 6.0, q5_0 5.5, q4_1 5.0, q4_0 4.5, iq4_nl 4.5.
* **양자화 V 는 Flash Attention 필수**(`-fa on`; `-fa auto` 면 자동 활성 + 로그 "enabling flash_attn since it is required for quantized V cache"). 블록 32 가 모든 후보의 head size(64/128/256/512)를 나눔.
* CUDA FA: 양자화 K/V 를 네이티브로 읽는 **벡터 커널**은 head 64/128/256 + `GGML_CUDA_FA_QUANTS` 로 컴파일된 쌍만. 기본값 **`q4_0-q4_0;q8_0-q8_0;f16-f16;bf16-bf16`**(대칭 쌍만; `all` 로 전 조합). 미컴파일 쌍(예: 릴리스 빌드에서 `q8_0-K/q4_0-V`) → "no FlashAttention vector kernel compiled … converting K and V to f16 instead (slow)". **따라서 릴리스 바이너리에서는 `q8_0/q8_0`, 비대칭 쌍은 §2(A) 처럼 자가 빌드 시에만**(크리틱 C16). 배치 >2(프리필) 또는 **head 512(Gemma 4 전역 레이어 5개)** 는 MMA 커널이 매 스텝 f16 변환 → Gemma 4 의 SWA 25층(head 256)은 네이티브, 전역 5층은 변환 비용.
* iSWA: 전역 캐시 = `-c` 셀, SWA 캐시 = `PAD(min(n_ctx, n_swa × n_seq + n_ubatch), 256)` 셀(`-ub 512` 면 +512 셀, `-ub 2048` 면 +2048). `--swa-full` 은 SWA 캐시를 전역 크기로 → **8GB 금지**(26B-A4B: 25층 × 8 KiB/토큰). 대신 서버의 컨텍스트 체크포인트 `-ctxcp`(기본 32, 호스트 RAM, SWA 윈도 비례, PR #15293). 드래프트/MTP 컨텍스트는 `-ctkd/-ctvd`.
* 회전은 head % 64 == 0 인 양자화 타입에 자동(모든 후보 해당). Gemma 4 MTP 드래프터는 q8_0 KV 에서 acceptance 0% 였다가 Q 회전 추가(2026-05-23, #23398 내부)로 수정 → 그 이후 빌드 사용.

**메커니즘** [H/M]:
1. **디코드(1토큰)**: CPU 전문가는 CPU 가 계산; 비용 = CPU 측 *활성* 전문가 바이트. gpt-oss-20b 전문가 1개 = 3 × 2880² × 4.25/8 ≈ **12.6 MiB(MXFP4)**, 4 활성 → 50 MiB/층, 24층 전부 CPU ≈ **1.18 GiB/토큰**(= 03장·06 의 1.27 GB, 단위 차이). Gemma 4 26B-A4B Q4_K_M 전문가 = 3 × 2816 × 704 = 5.95M 파라미터 ≈3.4 MiB, 8 활성 → 27.5 MiB/층, 30층 ≈ **0.81 GiB/토큰**(크리틱 C1 이 DeepMind 설정으로 재검증: 4.8 bpw 0.80 GiB / 4.5 bpw 0.75 GiB; 06 의 "1.5~1.8 GB" 는 2배 과대 → **26B-A4B 가 gpt-oss 보다 오프로드 친화적**). DDR5 상한: 5600 듀얼채널 89.6 GB/s(이론), 6000 96, 8000 128 — 그러나 **9700X 는 단일 CCD 라 Infinity Fabric 읽기 상한 ≈64 GB/s, AIDA64 ≈52 GB/s → 실효 50~60 GB/s 로 계획**(크리틱 C2; 05/06 의 60~75 GB/s 는 듀얼 CCD 9900X/9950X 급 수치). 순수 대역폭 상한 = 55 GB/s ÷ 토큰당 바이트: gpt-oss 전부 CPU ≈43 tok/s, 26B-A4B 전부 CPU ≈63 tok/s; 실제 커널은 ~50~70%.
2. **CPU 전문가 + 프리필**: ≥~32 토큰 배치는 op-offload → ubatch 마다 CPU 전문가 바이트를 **PCIe 5.0 x8(이론 ~32 GB/s, 실효 ~25~28; Gen4 슬롯이면 16)** 로 전송. gpt-oss 14층 CPU = ubatch 당 5.5 GiB ≈0.2 s → `-ub 512` 에서 ≈2.5k tok/s 전송 상한, `-ub 2048` 은 전송 4× 감소(gpt-oss 가이드가 `-ub 2048 -b 2048` 을 쓰는 이유)지만 컴퓨트 2.7 GB. 보고서 05 는 8GB 에서 `-ub 512`(VRAM 허용 시 1024) + 느린 프리필 감수, 06 은 프리필용 `-ub 2048` — **VRAM 잔여로 결정**(KV·캐시가 우선이면 512).
3. **`--moe-cache-mib`**: ≤32 토큰 배치(디코드·추측 검증)에 적용, 미스는 비동기 업로드, `--fit` 이 캐시를 반영. 크기 규칙(#30637/#30848): "토큰 1개분 전문가"(gpt-oss ≈1.18 GiB, 26B-A4B ≈0.81 GiB) 기준 ~1× 미만은 스래싱, 1.4~1.8× 이상에서 SLRU > LRU; am17an: PCIe 4.0 에선 적중률 <~75% 면 무익, 5.0 은 더 관대; 저자 경험칙 ≈전체 전문가 바이트의 10%. **#31421(10-30, open, 수정 없음)**: #30637 이후 작은 캐시 적중률 37.5% → 0.6%, tg 12.9 → 8.8 회귀; Q4_0 전문가는 `-nr` 없으면 캐시 자동 비활성 → 층당 ≥16 슬롯(26B Q4_0 ≈1.5 GB) 또는 #30637 이전 빌드. 후속 **전부 미머지**(크리틱 C20, 11-04 확인): `--moe-cache-cpu-share F` + `scripts/moe-cache-tune.py`(PR #30966, open, 11-03 force-push), `auto`(#31286, open draft), `--moe-direct-io`(#31469 RFC). 즉 아래 RTX 3070 수치는 **PR 브랜치 빌드**가 필요하다.

**CPU 전문가와의 상호작용**(분석, 미측정) [M]: n 개 드래프트 검증은 MoE 층이 n+1 토큰이 고른 전문가의 *합집합*을 읽음; gpt-oss(32 중 4)·Gemma 4(128 중 8)에서 합집합은 n 에 거의 선형 증가 → 전문가가 RAM 바운드면 검증 1회 ≈ 디코드 n 회 비용, 가속은 1× 로 붕괴(GPU 상주 gpt-oss EAGLE-3 결과와도 일치). 이득 조건: (a) 전문가 대부분 GPU, (b) MoE 캐시 적중률 높음, (c) acceptance 매우 높음(코드 복창). MoE 캐시는 ≤32 토큰 검증 배치에 적용되지만 #31497 은 *드래프트* 모델 제외를 제안.
