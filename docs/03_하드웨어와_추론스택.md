## 2. 디코드 속도 산술

* 실측 기준점: Llama-2-7B Q4_0(3.83 GB) → **tg128 93.5 tok/s**(FA on), pp512 4,195 tok/s [H, llama.cpp 토론 #15013] ⇒ 실효 358 GB/s(≈ 80 %).
* 규칙: `tok/s ≈ 360 ÷ (가중치 GB + KV GB 읽기)`. 4.9 GB(8B Q4_K_M) ≈ 70~73, 5.5 GB(12B ~3.7bpw) ≈ 60~65, 7.0 GB ≈ 50.
* CPU 쪽 전문가(MoE) 디코드: `tok/s ≈ 55 GB/s ÷ 토큰당 CPU 가 읽는 전문가 바이트`. gpt-oss-20b 는 전부 CPU 에 두면 토큰당 1.27 GB → 상한 43, 실효 60~70 % → **25~30 tok/s**; 전문가 8~10층을 GPU 에 두면 **30~40**; `--moe-cache-mib` 적중률 70~90 % 에서 추가 1.6~2.2× (RTX 4090/5090 측정치, 8GB 카드는 캐시 용량이 작아 효과 축소 예상).
* 9700X 참고 실측: Ryzen 9 5900X + DDR4-3200(51 GB/s) + 7900 XT, gpt-oss-20b `-cmoe` → ~20 tok/s, `-ncmoe 8` → ~38, `-ncmoe 4` → ~60, 전부 GPU → ~94 [H, llama.cpp 토론 #15396]. 9700X 는 대역폭이 비슷하므로 같은 범위 예상.
* PCIe 5.0 ×8 ≈ 32 GB/s(Gen4 슬롯이면 16 GB/s). `--moe-cache-mib` 의 미스 트래픽이 PCIe 를 타므로 **Gen5 ×16 슬롯(B650E/X670E/B850/X870)** 권장.

## 3. llama.cpp 핵심 플래그 (b12086 소스에서 확인)

| 범주 | 플래그 |
|---|---|
| 오프로드 | `-ngl N\|auto\|all`(기본 auto), `-ot "<regex>=CPU"`, `-cmoe/--cpu-moe`, `-ncmoe/--n-cpu-moe N`, **`-ncffn/--n-cpu-ffn N`**(밀집 FFN), **`--moe-cache-mib N`** |
| 자동 맞춤 | `-fit on\|off`(기본 on), `-fitt/--fit-target MiB`(기본 1024), `-fitc/--fit-ctx N`(기본 4096), `-fitp/--fit-print on` |
| 어텐션/KV | `-fa on\|off\|auto`, `-ctk/-ctv {f32,f16,bf16,q8_0,q4_0,q4_1,iq4_nl,q5_0,q5_1}`, `--swa-full`, `-kvu`, `-ctxcp`, `-cram` |
| 배치 | `-b`(2048), `-ub`(512; 전문가가 CPU 면 2048~4096 권장) |
| 로딩 | `-lm/--load-mode {auto,mmap,mlock,dio,…}`, `-lzm/--lazy-mode`(Gemma PLE 등 큰 임베딩을 디스크에서 필요 행만) |
| 추측 디코딩 | `--spec-type {draft-simple,draft-eagle3,draft-mtp,draft-dflash,draft-dspark,ngram-simple,ngram-map-k,ngram-map-k4v,ngram-mod,ngram-cache}`, `-md`, `-ngld`, `--spec-draft-n-max`(3) |
| 빌드 | `GGML_CUDA_FA_QUANTS`(기본 `q4_0-q4_0;q8_0-q8_0;f16-f16;bf16-bf16`, `=all` 로 전 조합), `GGML_CUDA_MMQ_PREC={auto,q8,q4}`(런타임 env; `q4` = NVFP4/MXFP4 층을 W4A4 네이티브로) |

## 4. GGUF 저정밀 타입 (ggml.h / ggml-common.h)

| 타입 | 블록 구조 | bpw |
|---|---|---|
| MXFP4 (=39) | 32 × E2M1 + 1 × E8M0 스케일 | 4.25 |
| NVFP4 (=40) | 64 × E2M1 + 4 × UE4M3(16개당 1개) + 텐서별 F32 스케일 | 4.5 |
| Q1_0 (=41, 2026 신규) | 1비트 + 그룹 스케일 | 1.125 |
| Q2_0 | 2비트, 그룹 64 | 2.25 |
| TQ1_0 / TQ2_0 | 삼진(BitNet) 패킹 | 1.69 / 2.06 |
| IQ4_XS / IQ3_M / IQ3_XXS / IQ2_M / IQ2_XXS | 코드북(비선형·E8 격자) 기반, imatrix 권장(IQ2_XXS/IQ2_XS/IQ1_S 는 필수) | 4.25 / 3.66 / 3.06 / 2.7 / 2.06 |
| Q4_K_M / Q5_K_M / Q6_K / Q8_0 | 슈퍼블록 256 K-quant / 블록 32 | 4.85 / 5.69 / 6.56 / 8.5 |

`llama-quantize` 의 기본 ftype 목록에 NVFP4 는 없습니다(PR #23572 미채택). NVFP4 GGUF 는 ModelOpt·compressed-tensors NVFP4 체크포인트를 `convert_hf_to_gguf.py` 로 변환해 얻는 것이 공식 경로입니다. (`--tensor-type …=nvfp4` 우회는 실험적 — `recipes/README.md` 참고.)

## 5. 다른 스택 요약

* **ik_llama.cpp**: CPU/하이브리드 MoE 에 강점(IQ*_K/IQ*_KT 트렐리스, Gyro Trellis 2026-11, AVX-512 최적화 빌드 PR #2818), 그러나 sm_120 에서 MXFP4 MoE 관련 미해결 버그(#2484, #2519, #2525)와 Gemma 4 26B-A4B 에서 업스트림 대비 TG 4.4× 느린 보고(#1765) → **이 장비의 하이브리드는 업스트림 llama.cpp 우선**.
* **Ollama** v0.40.14: `OLLAMA_KV_CACHE_TYPE`, DFlash 자동 감지. NVFP4 GGUF 는 스톡 빌드에서 거부 보고(sm_120 커널 없음) → 미검증/비권장.
* **LM Studio** 0.4.28: 런타임 llama.cpp b11337 기반(NVFP4/MTP 머지 이후), "expert offload" 옵션 제공. CUDA 12 런타임이 `120a` 로 컴파일됐는지는 미문서 → NVFP4 GGUF 로 직접 테스트.
* **SGLang**: SM120 NVFP4 는 FlashInfer CUTLASS/b12x 경로. 메모리 현실은 vLLM 과 동일.

## 6. 미해결 질문

1. 9700X 단독/하이브리드 MoE 의 공개 llama-bench 수치 없음 → 로컬 `scripts/60_bench.sh` 스윕으로 확정 필요.
2. 8GB 5060 Ti 전용 LLM 측정치 없음(모두 16GB). 대역폭 동일 논리는 견고하나 Windows 에서 5~6 GB 모델 옆에 남는 KV 용량은 로컬 측정 필요.
3. LM Studio/Ollama 번들 런타임의 `120a` 컴파일 여부.
